# M1.2 realtime playback

The hardware-independent `playback` module renders exactly one finite source:
a sine tone or validated, interleaved, prepared f32 PCM. A prepared buffer must
match the stream's explicit rate/channel count, contain whole frames, and have
finite samples in [-1, 1]. There is no resampling, file decoder, mixer, effect,
cue routing, or live scheduler. The CPAL adapter alone owns device handles and
streams. M0 timing/scheduler implementations are unchanged.

The CLI buffer mode compiles four impulses at 120 BPM using M0's TempoMap and
OfflineScheduler, renders offline in 127-frame blocks, and duplicates the mono
fixture into the requested channels before stream creation. Impulses occur at
source frames 0, 24000, 48000 and 72000 at 48 kHz. This connects deterministic
M0 preparation to realtime delivery without imposing M0's 8192-frame block
limit on device callbacks. Tone mode generates a 440 Hz, amplitude 0.1 sine.
Both sources last two seconds and end in silence.

## CLI and configuration

```
cargo run -p audio-backend --example playback --locked --offline -- tone
cargo run -p audio-backend --example playback --locked --offline -- buffer
# mode, fresh output ordinal (or default), Hz, channels, requested buffer frames
cargo run -p audio-backend --example playback --locked --offline -- tone default 48000 2 default
```

The CLI requests f32; the library additionally supports i16, i32 and u8. Rate,
channels, encoding and buffer request are checked against correlated CPAL rows.
Unsupported requests fail explicitly. Default selects the OS default endpoint;
an ordinal selects a fresh enumeration entry and is not persistent identity.
No fallback to another device/configuration occurs. Fixed buffer sizes are
requests, not callback length promises. Unknown limits defer validation to CPAL.

## Callback and lifecycle contract

Construction validates parameters, allocates PCM/shared state, queries hardware,
and builds a paused stream on the control thread. Start/stop are control-thread
operations, idempotent in their respective states. Stop is terminal and rejects
restart. Drop mutes and destroys the stream even on early CLI errors/timeouts.
Pause/build/play errors propagate with operation context. A failed pause still
leaves the source disabled; dropping the owner releases the stream. Device
disconnect/runtime errors latch an atomic failure flag and disable subsequent
rendering. No callback logging or error-string formatting occurs; asynchronous
error detail is deliberately reduced to a failure flag. Recreate a stream to
recover. One already-running callback or queued endpoint audio can finish after
a stop/error request; this is not a sample-accurate abort or drain API.

The data callback performs slice writes, scalar synthesis/conversion and atomic
loads/stores only. It acquires no mutex, blocks on nothing, does no filesystem
I/O, and allocates or frees no heap ownership. Source ownership is fixed until
stream destruction; no callback-side buffer replacement or reference-count
operations occur. CPAL owns its platform callback infrastructure. These claims
are based on source inspection, not allocator or deadline instrumentation.
The x64 target has native 64-bit atomics. Callback length is unrestricted; a
trailing partial frame is silenced defensively. EOF and disabled/failed sources
produce format-correct silence, including unsigned PCM midpoint silence.

`sample_clock` starts at zero for a newly built stream and counts whole frames
delivered to data callbacks, including silence. It is monotonic and saturates at
u64::MAX. `source_frames` counts consumed frames and stops at source EOF; callback
partitioning never changes source order or tone phase. Neither counter is a DAC
presentation timestamp or the signed M0 musical timeline. Prepared source frame
zero maps to the first enabled callback frame. Monitor fields are independently
observed atomics, not a coherent transactional snapshot. Control communicates by
an enabled flag and reads telemetry; there is no unbounded command queue.

## Windows verification

Local Windows x64 MSVC, Rust 1.85.1, CPAL 0.15.3/WASAPI:

| Setting | Observed/requested value |
| --- | --- |
| OS default output | Speakers (HyperX Cloud III S Wireless) |
| Requested rate / channels / encoding | 48000 Hz / 2 / f32 |
| Buffer request | Default (not a fixed physical buffer size) |
| Largest observed callback | 1056 frames |
| Tone source frames | 96000, finished=true, failed=false |
| Buffer source frames | 96000, finished=true, failed=false |
| Initial tone/buffer device-frame totals including trailing silence | 105696 / 106176 |

Both CLI modes started, delivered the complete source and stopped successfully.
The demo also exercises repeated start/stop and rejection of restart after stop.
This proves successful stream delivery, not human-confirmed audibility, measured
latency, underrun absence, exclusive-mode behavior or acoustic correctness.
The CLI allows 200 ms trailing silence before stop; this is a best-effort tail
delay, not a measured drain guarantee. Physical disconnect recovery was not tested.

Focused tests cover exact PCM order, variable/empty/oversized callbacks, tone
partition invariance, EOF silence, disabled/error silence, unsigned conversion,
clock accounting and source validation. Workspace fmt/check, Clippy with warnings
denied, tests and the Windows dependency inventory gate pass. No external
dependency was added; only existing workspace crates are example dependencies.
GPL-3.0-or-later licensing and the seven-package Windows inventory remain intact.
Cargo-deny is unavailable locally; no new advisory scan is claimed.
