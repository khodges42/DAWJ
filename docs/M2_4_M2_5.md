# M2.4 eight-part deck mixing and M2.5 expressive controls

The live engine retains two independent decks with `parts::SLOTS` (eight)
addressable slots each. Each slot owns its own playback cursor, Part lifecycle,
gain/filter state and diagnostics even when slots share a resident asset template.
The existing scheduler applies simultaneous launches/stops before the target
sample. No scene, instrument, effects graph or GUI was added.

## Signal path and headroom

Each active slot reads its resident stereo sample, applies its stereo low-pass
and smoothed gain/mute, and contributes 1/SLOTS to its own stereo deck bus.
The divisor is fixed: adding/removing a voice never renormalizes the other parts.
Gains are limited to [0,1], the non-resonant filter cannot amplify bounded input,
and eight full-scale voices can sum to at most unity before the deck mixer.
Existing deck gain, crossfader curve/ramping, master headroom/limiter and separate
cue protection/mapping are preserved. Part controls affect both master and cue;
cue still selects deck buses before the crossfader.

Stopped or merely queued-to-start slots perform no sample read, gain ramp or
filter update. Their processed-frame counters do not advance. Fixed address
checks, scheduler scans and callback diagnostics still inspect the small slot
array. Muted Playing slots remain active: they advance source phase and filter
history so unmuting cannot restart the sample or expose stale filter history.
Normal one-shot EOF and scheduled stops still remove the active slot; residual
filter tails are not rendered after stop. Arbitrary nonzero stops/replacements
retain the previously documented interruption/click limitation.

## Parameters and smoothing

`Request::Parameters(PartParameters { gain, muted, cutoff_hz })` uses the same
bounded SPSC FIFO and ticket mechanism as musical actions. Parameters require
Immediate policy and apply to the next callback-entry snapshot. A parameter
request neither supersedes nor cancels a queued launch/stop/replacement. Queue
overflow is an admission error; invalid/rate-incompatible requests are rejected
without changing the previous parameters. Callers send a complete parameter
snapshot, preserving their desired gain when setting/clearing mute.

Gain is encoded with 16-bit linear resolution; cutoff is rounded to whole Hz.
Gain must be finite in [0,1]. Cutoff is None for bypass or a finite value in
[20, min(20000, 0.45 * sample_rate)] Hz. The producer rejects malformed values;
the audio consumer also enforces the actual stream-rate limit. Applied parameter
tickets mean the ramp target was accepted, not that the ramp has finished.

Active gain changes ramp linearly over sample_rate/50 frames (20 ms at the
supported common rates). Mute sets the effective gain target to zero using the
same ramp; unmute ramps back to the supplied gain. Retargeting starts from the
current value, so rapid updates remain continuous. Multiple parameter requests
in the same entry batch settle on the last valid target before audio renders.
Inactive parameters settle immediately because there is no audible source;
a part muted before launch therefore emits no initial blip.

## Low-pass stability and state

Each stereo channel uses a first-order low-pass:

`y[n] = y[n-1] + alpha * (x[n] - y[n-1])`

The target coefficient is `1 - exp(-2*pi*cutoff/sample_rate)`. Bypass targets
alpha=1 and copies the current input exactly once settled. Coefficients ramp
linearly over the same 20 ms interval; they stay in [0,1], including during
bypass transitions. The recurrence is therefore a convex combination of bounded
input and previous state. There is no resonance, feedback-gain control, boost or
unstable coefficient region. A final state clamp suppresses rounding overshoot;
states below 1e-20 are flushed to zero to avoid denormal accumulation.

Filter history is preserved on cutoff, gain, mute and active retrigger/replacement
changes. Only a genuinely new start from inactivity clears channel history.
Gain and coefficient ramp progress survive parameter retargeting. This is a
gentle 6 dB/octave low-pass, not a resonant performance filter or an effects rack.
It does not repair discontinuities already present in Preserve-mode sample data.

## Observable state and metering

`LiveControl::slot(deck, slot)` provides the last completed nonempty callback's lifecycle
label, PartId, consumed source frames, stereo peak, cumulative processed-frame
count, accepted parameter target and engine-closed flag. QueuedStart reports
its requested PartId; active states report the current PartId. A stopped slot
reports no PartId and position zero. Source position is the consumed frame count
within the current playback instance, reset on replacement/retrigger; it is not
the wrapped asset frame index.

Peaks are absolute post-filter/post-gain, before the fixed 1/SLOTS deck sum, over
the most recent callback. They reset each callback and are zero for inactive
parts or settled muted parts. Left/right peaks share one atomic word. Other
fields are independently observed atomics, so readers must not treat a snapshot
as a transactional acknowledgement or use these diagnostic values for timing.
The scheduler and command tickets remain authoritative for applied events.

The callback performs fixed-size DSP and atomic publication. All arrays are
constructed before playback. No blocking, filesystem I/O, heap allocation or
ownership replacement was introduced in rendering. Filter exponentials are
computed only when parameter requests are ingested, at most the queue's bounded
32 requests per callback, not per sample. Stopped slots skip DSP entirely.
No new hard realtime or dropout guarantee is claimed without hardware/load tests.

## Offline CLI and verification

Generate a fixture, then run the stdin-driven offline test interface:

```
cargo run -p audio-backend --example sample_parts --locked --offline -- --fixture target/m2-fixture.wav
cargo run -p audio-backend --example part_controls --locked --offline -- target/m2-fixture.wav target/parts.wav
```

Enter commands such as:

```
launch 0 0
launch 1 7
render 4800
set 0 0 0.5 false 400
set 1 7 1 true off
render 4800
status 0 0
status 1 7
stop 0 0
render 480
quit
```

The interface writes four-channel PCM16 at 48 kHz (master L/R, cue L/R); cue
selects B. Commands and all WAV writing run outside render. The CLI never opens
an output device. Render is bounded per command and output RIFF size is checked.
For actual stream playback, the same `Request::Parameters` API is usable while
`CpalPlayback::open_live` owns the engine; no separate audio command mechanism
was introduced.

The example above rendered 10080 frames. Snapshots at frame 9600 showed both
parts still Playing at source position 9600, A with gain approximately 0.5 and
400 Hz cutoff, B muted with zero callback peak. No audible playback was performed.
Tests cover sixteen simultaneous voices, fixed summing, silence/idle processing,
deck independence, master/cue preservation, parameter rejection, pre-launch mute,
DC/high-frequency response, gain ramps, stereo polarity, rapid limit changes,
filter-history retention and exact callback-partition invariance. Existing M0–M2.3
tests remain in the workspace gate. All 65 tests, fmt, workspace check, Clippy
with warnings denied, doc-tests and the unchanged Windows dependency audit passed.
No new dependency, ASIO backend, GUI, scenes,
MIDI instrument or general-purpose effects system was added.
