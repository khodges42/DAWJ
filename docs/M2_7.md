# M2.7 first playable performance demonstration

`cargo run -p audio-backend --example performance` is a temporary line-oriented
performance harness around the existing M2 engine. All composition preparation,
input parsing, console formatting and file writing occur outside audio rendering.
The harness/support code lives under `examples/`, is shared by integration tests,
and is not an application framework or a proposed final GUI architecture.

## Two prepared demo compositions

Both compositions use the shared 120 BPM, 48000 Hz transport and eight-bar phrase
epochs. Each provides eight slots with a distinct Part/Asset identity:

| Slot | Role | Copper Steps (A) | Glass Tide (B) |
| --- | --- | --- | --- |
| 1 | kick | Low pitched pulse | Brighter pitched pulse |
| 2 | snare | Deterministic noise backbeat | Different deterministic noise seed |
| 3 | hats | Eighth-note noise gates | Alternate stereo balance/noise |
| 4 | bass | C-based repeating figure | E-flat-based figure with octave variation |
| 5 | chord | Soft C-based chord | E-flat-based chord |
| 6 | arp | Higher gated figure | Transposed gated figure |
| 7 | shaker | Sixteenth-note texture | Alternate stereo texture |
| 8 | fill | One-bar noise/tonal roll, OneShot | Transposed OneShot roll |

Slots 1–7 are resident one-bar loops. Slot 8 is explicitly OneShot so manual
fills do not keep looping after EOF. The samples are generated deterministically
in memory, encoded as float WAV and decoded/prepared through the M2.2 loader
before constructing the stream. No third-party samples, files, proprietary
instruments or downloaded content are used. The original generator and its
generated demo audio are provided under GPL-3.0-or-later. Preparation uses the
existing 64-frame edge fades. The source levels, fixed eight-slot summing,
deck gains and master/cue limiters keep output conservative.

## Reproduce without starting sound

```
cargo run -p audio-backend --example performance --locked --offline -- --help
cargo run -p audio-backend --example performance --locked --offline -- --render target/performance.wav --script docs/examples/m2-performance.txt
cargo run -p audio-backend --example performance --locked --offline -- --check
cargo test -p audio-backend --test performance --locked --offline
python scripts/validate_m1.py
```

The default offline output has four channels: master L/R, then cue L/R.
Use `--channels 2` for a master-only render. A multichannel WAV is digital routing
evidence; a media player's downmix does not provide private headphone monitoring.
With no script, enter commands interactively on stdin. `wait` advances offline
rendering; other commands are queued until the next render opportunity.

## Live playback and device selection

Playback requires explicit `--play`. The program prepares all assets, validates
the requested device configuration, identifies the endpoint/routing, then gives
a three-second countdown before starting. No audio device is opened in render
mode. `--check` constructs/drops a paused stream and never starts playback.

```
cargo run -p audio-backend --example performance --locked --offline -- --devices
cargo run -p audio-backend --example performance --locked --offline -- --play
cargo run -p audio-backend --example performance --locked --offline -- --play --script docs/examples/m2-performance.txt
# Only after verifying the intended interface, stream channel count and mapping:
cargo run -p audio-backend --example performance --locked --offline -- --play --device <ordinal> --channels 4
```

Live mode defaults to stereo master-only. Cue requests explicitly report
unavailable and leave cue routing off; the provided script continues with this
limitation so it can demonstrate the transition on stereo headphones. Four-channel
mode requests master [0,1], cue [2,3] and reports SeparateChannelsUnverified.
It fails if the actual WASAPI endpoint lacks the requested format; it does not
silently substitute another device or pretend to provide private cue. Device
ordinals are transient. The existing low-level routing API remains available for
other physical maps; this temporary CLI only exposes the standard two/four-channel
layouts.

Input reads run on a separate thread with a bounded control-side channel. The
control loop polls stream errors while waiting for lines. No stdin operation,
channel receive, sleep or console output runs in the audio callback. The input
thread may be waiting on stdin when the program exits; it is intentionally not
joined from the audio/lifecycle path. On EOF/quit, deck gains fade to zero for
100 ms before stop. Errors retain the existing stream-destruction safety behavior.

## Controls and performance walkthrough

Select deck with `deck a` or `deck b`. Slot numbers are **1 through 8**:

| Command | Action |
| --- | --- |
| `quant immediate/beat/bar/phrase` | Change launch/stop/retrigger policy |
| `launch 1`, `stop 1`, `retrigger 1` | Address selected deck's slot |
| `gain 4 0.7` | Smoothed per-part gain |
| `cutoff 5 900`, `cutoff 5 off` | Smoothed low-pass/bypass |
| `mute 3 true`, `mute 3 false` | Smoothed mute/unmute |
| `fill bar` | One-time fill at next bar; default uses current quantization |
| `every 2 bars`, `every 4 beats` | Recurring fill rule on slot 8 |
| `phrasefill 8` | Deck-relative eighth-bar fill every eight-bar phrase |
| `rule off/on/cancel` | Disable, enable or remove slot 8's rule |
| `cross 0` through `cross 1` | Smoothed A-to-B equal-power crossfader |
| `cue a/b/both/off` or `cue` | Select cue, or toggle selected deck's cue bit |
| `status` | Both decks' Playing/QueuedStart/QueuedStop/etc. states, cursors, gains, cutoff, meters and rule counters |
| `wait 4` | Advance/wait for four beats of the fixed-120-BPM shared transport |
| `quit` | Fade and shut down |

Status also shows the last 32 command ticket outcomes. They are bounded diagnostic
observations and may expire as in M2.3; submitted commands are not reported as
playing until the audio engine applies them. Slot snapshots are from the last
completed callback and are not a transactional transport view.

The supplied [script](examples/m2-performance.txt) is the reference walkthrough:

1. Start A's kick and hats with crossfader fully A; add backbeat, bass and chord
   at bar quantization. Lower bass gain, filter the chord, and trigger one fill.
2. Select B and launch its kick, hats, bass and arp. Select B cue where separate
   outputs exist. Install a two-bar recurring fill while A remains on master.
3. Move crossfader through 0.25, 0.5, 0.75 and 1 over successive four-beat spans.
   Both decks' source cursors keep running throughout; crossfading does not start
   a second transport or rewind B.
4. Stop A's parts, leave B running, install and then cancel a phrase-fill rule,
   inspect states, and quit through the controlled fade.

The script has 36 beats, plus 100 ms final silence/fade preparation, giving an
offline final global frame of 868800. Live `wait` polls the rendered source clock,
not a musical wall-clock timer; only control-side sleep is used between polls.
Live input admission can miss an exact boundary by a callback, according to
M2.3's documented arrival semantics. Consequently the offline trace is the
deterministic reference; identical wall-clock admission frames are not promised
for the live script. This fixed-tempo harness is not a tempo editor.

## Verified behavior and remaining hardware gates

All 80 workspace tests, fmt/check, Clippy with warnings denied, doc-tests and the
unchanged seven-package dependency audit pass. New integration tests execute the
same parser/support code as the executable. They verify:

- identical full-walkthrough audio fingerprints at 127- and 512-frame callbacks;
- both compositions' sixteen distinct Part identities and OneShot fill completion;
- monotonically continuous shared transport and B cursors through the transition;
- A stopped while B remains active, and actual recurring fills firing;
- B audible on the logical cue bus with exactly zero master contribution while
  the crossfader is closed, followed by nonzero master without cursor reset;
- explicit stereo cue unavailability, queued/stopped display and invalid controls.

The script actually rendered 868800 frames of four-channel PCM16 at 48 kHz.
Measured sample peaks were 109 PCM16 counts on master and 89 on cue; the deliberately
quiet output is nonzero and below the master ceiling. Paused stream checks passed
on HyperX Cloud III S Wireless (stereo f32) and DualSense Wireless Controller
(four-channel f32), both at 48 kHz/default buffer request.

No audible playback or fresh live soak was started during this task. Human
listening, performance feel, live control/underrun behavior under load, DAC latency,
physical channel order and private headphone isolation still require controlled
hardware validation. The DualSense's channel report is not a validated DJ
main/headphone interface. The eventual interface may need ASIO if its independent
outputs are unavailable via WASAPI; ASIO remains disabled and subject to the
existing dependency/SDK review. No zero-dropout or physical cue claim is made.
