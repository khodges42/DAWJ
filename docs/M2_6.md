# M2.6 periodic triggers and one-time fills

Declarative `TriggerRule` values compile into fixed runtime records in the
existing `MusicalScheduler`. Each of the sixteen part slots can hold one rule,
independently of its pending manual action. Rules reuse M0's global musical
clock, absolute beat/frame conversion and quantization. No timer, probability
generator, new timing system or dynamic callback event list was introduced.

## Rule vocabulary and phase

| Rule | Musical grid | Repetition |
| --- | --- | --- |
| `Once { boundary }` | Next unrendered Immediate/Beat/Bar/Phrase boundary from M2.3 | Exactly one opportunity, then spent |
| `Every { n, unit, phase }` | Every 1..=1024 beats or bars; bar = four quarter notes | Repeating |
| `PhraseBar { bar, phrase_bars, phase }` | Start of a one-based bar in a repeating four- or eight-bar phrase | Once each phrase |

`RulePhase::Global` anchors the grid to beat zero. For Every, n=2 bars means
global ticks 0, 7680, 15360, and so on. For PhraseBar the declared phrase length
defines that global repeating grid independently of a deck's configured length.

`RulePhase::Deck` anchors to the addressed deck's configured epoch. A deck-relative
PhraseBar requires the declared four/eight-bar length to match that deck's phrase
length. The selected bar offset is `(bar-1)*3840` ticks. Example: bar eight in an
eight-bar phrase means epoch+26880 ticks, then every 30720 ticks. Deck A and B
may have different epochs. Manual launches/retriggers do not move these grids.
There is no part-relative rule phase; a Part's nominal musical length and source
sample loop length never define a recurrence grid.

Once uses the existing M2.3 boundary policy: Beat/Bar are global, Phrase uses the
target deck's epoch, and Immediate is the first renderable frame after admission.
Musical boundaries are inclusive only while their rounded output frame remains
unrendered. Mid-callback requests wait for the next entry snapshot; no missed
occurrences are replayed. Invalid periods, bars, phrase lengths or source indices
reject without replacing a previous valid rule.

## Rule lifetime and source behavior

The prepared bank supplies the target Part. Each occurrence starts a stopped
slot, retriggers a playing matching Part, or replaces a playing different Part.
The sample cursor resets to one-shot frame zero or the configured loop start.
Normal per-part gain/filter and deck/master/cue processing remain in place.
Source and filter interruption behavior is unchanged from M2.3/M2.5.

A Once rule is consumed at its selected opportunity, whether it fires or loses
to a manual action. It never rolls forward to another boundary. Enabling a
spent Once rule rejects: install a new rule explicitly to rearm it. This protects
one-time fills from accidental recurrence on enable/disable toggles. Installing
a rule is an intentional rearm/replacement even if its value equals the old one;
it resets the rule's counters. Last valid installation in an entry batch wins.

Rule lifetime and sample playback mode are separate: for a one-shot drum fill,
select a resident Part with `PlaybackMode::OneShot`. It naturally stops at EOF,
while a recurring rule remains armed for its next occurrence. A Once rule aimed
at a Loop Part launches that declared loop once; it does not silently change the
asset's playback mode or stop it at a nominal musical length.

## Manual interaction and cancellation precedence

1. The existing command queue is consumed in FIFO order at callback entry.
2. Eligible manual actions apply first at each output frame.
3. Rules are checked in deck/slot order after manual dispatch.
4. A pending manual action reserves its slot. Rule occurrences during that wait,
   and on the frame a manual action is accepted/applied, are skipped, not delayed.
5. Consequently a quantized launch/retrigger and a rule on the same slot/frame
   produce only the manual trigger. Invalid/rejected manual commands do not
   suppress valid rule work. A successful manual cancellation also reserves its
   admission frame so cancelling a launch does not reveal a hidden rule trigger.

Manual Stop disables the current rule immediately when the stop request is
accepted, including for a future quantized stop. This prevents automation from
restarting a deliberately stopped part. Cancelling that stop does not re-enable
the rule; explicit EnableRule or a new installation is required. Other manual
launch/replace/retrigger commands allow future rule occurrences to resume after
the pending action finishes. They are not a permanent override of automation.

`EnableRule(false)` removes future eligibility but retains configuration/counters.
`EnableRule(true)` on an unspent disabled rule recompiles its next unrendered
matching grid boundary, preserving global/deck phase and doing no catch-up.
Enabling an already enabled rule is idempotent. `CancelRule` removes the rule
and is idempotent even when absent. Neither operation stops the active source
nor cancels an unrelated manual command; use manual Stop for that. Administrative
changes admitted exactly at a boundary precede rule dispatch at that frame.

All three rule requests require outer `Quantize::Immediate`; the rule itself
declares the musical schedule. Existing Ticket outcomes acknowledge installation,
enable/disable or cancellation, not each future occurrence. Per-slot diagnostics
add installed/enabled/spent flags and saturating fired/skipped counters. Skipped
counts conflict opportunities; explicitly disabled rules have no opportunities.
Counters persist while disabled and reset on a new installation/removal.

## API example

After preparing a OneShot bank entry and an eight-bar deck phrase:

```rust
use audio_backend::live::{Request, Quantize, TriggerRule, RulePhase};
// `control` is the existing single producer; `fill_bank_index` is preloaded.
control.submit(0, 7, Request::Rule {
    bank: fill_bank_index,
    rule: TriggerRule::PhraseBar { bar: 8, phrase_bars: 8, phase: RulePhase::Deck },
}, Quantize::Immediate)?;
control.submit(0, 7, Request::EnableRule(false), Quantize::Immediate)?;
control.submit(0, 7, Request::EnableRule(true), Quantize::Immediate)?;
control.submit(0, 7, Request::CancelRule, Quantize::Immediate)?;
```

For a single fill at the next bar, install
`TriggerRule::Once { boundary: Quantize::Bar }`. For every two beats, use
`TriggerRule::Every { n: 2, unit: RuleUnit::Beats, phase: RulePhase::Global }`.

## Tempo, work bounds and traces

Rule deadlines remain BeatTicks across tempo edits. Each next occurrence is
derived by adding an exact period to its previous musical deadline, never a
rounded frame period or wall-clock interval. Eligibility is recalculated through
the edited TempoMap, including fractional frame anchors and near-boundary inverse
rounding. Source samples still play at their prepared native rate; tempo edits
do not time-stretch them.

There are at most sixteen compiled rules. Each frame dispatches at most sixteen
manual actions plus one occurrence per rule. A recurring period is at least one
beat; at supported rates/tempos this is many samples, so there is no unbounded
catch-up loop. Rule compilation, phase arithmetic and validation are bounded;
all storage is constructed before streaming. No allocation, locking, decoding,
file access or buffer ownership replacement occurs in callback rule processing.
Tick overflow or exhausted map horizon uses the existing latched failure path.

Recurring actions can exceed the old sixteen-event diagnostic trace in one long
callback. The fixed trace now holds the first 128 events, each labeled Manual
or Rule. `LiveEngine::dropped_events()` reports omitted trace entries for that
callback; it does not report dropped audio actions. All actions still dispatch,
and fired counters include them. Offline event-trace comparisons must use blocks
small enough to avoid truncation, or inspect that counter explicitly. No unbounded
trace vector was added to rendering.
