# M2.3 quantized live arrangement scheduling

The `event-engine::live::MusicalScheduler` extends the existing M0 scheduler
crate. It uses the same `TempoMap`, `BeatTicks`, `SampleFrame`, absolute rounding
and epoch-aware quantization as M0. M0's frozen offline impulse scheduler remains
unchanged. The M2 Part reducer owns lifecycle transitions; the live scheduler
adds sample-frame eligibility and applies one due slot at a time. No separate
wall-clock transport or timer drives musical actions.

## Clocks and quantization

One callback-owned global frame clock starts at zero. Both decks and all sixteen
slots render on it. It advances even with every part stopped, permitting later
launches. Empty/partial-only buffers do not advance it or admit commands. This
is a rendered-frame clock, not a DAC presentation timestamp. The existing CPAL
monitor's delivered-frame clock can additionally count disabled silence; its
`source_frames` field reports this live engine's global frame position.

| Policy | Eligibility |
| --- | --- |
| Immediate | First frame of the next nonempty callback whose command snapshot includes the request |
| Beat | Next unrendered global multiple of 960 ticks |
| Bar | Next unrendered global multiple of 3840 ticks (fixed 4/4) |
| Phrase | Next unrendered multiple of that deck's phrase length relative to its epoch |

Boundary inclusion is decided in frame space: a rounded boundary frame equal
to the current frame is eligible, a rendered one is missed. Beat-to-frame
conversion uses M0's absolute nearest-frame rounding. The scheduler checks the
preceding grid boundary as well because at high tempos a boundary's rounded
frame can invert to the following tick. Immediate uses an explicit frame
deadline, avoiding any delay caused by inverse tick rounding.

Deck epochs/phrase lengths are configured before streaming; initial epochs must
be <= zero (equivalent positive phase offsets can be normalized by the phrase
length). Deck phrase phase is independently computed from the global map and
epoch. Part musical phase is relative to its most recent start/retrigger and
nominal musical length. These phase queries have BeatTicks storage precision;
sample cursor reset and event delivery use exact output frames. Replacing or
retriggering a part never resets global/deck phrase time.

## Command precedence and callback boundaries

`LiveControl` is the single producer; it may move to a dedicated control thread
but is not cloneable. It submits small Copy commands to a 32-entry SPSC ring.
The consumer takes one publication snapshot per nonempty callback. Arrivals
after that snapshot wait until the next callback, even if their preferred
boundary lies later inside the current buffer. An arrival just after a boundary
therefore targets the following boundary; it cannot rewrite already rendered
samples. There is no promise of sample accuracy relative to an OS input timestamp.

The consumer processes the snapshot in FIFO order before dispatching events at
that callback's first frame. M2.1 transition rules remain authoritative: one
pending action per slot, latest valid pending request wins, conflicting Start
against an active different Part rejects, and invalid requests leave the old
pending state untouched. Cancel names the pending command ID. A matching cancel
at the boundary wins if it is in that entry snapshot; a stale/already-applied ID
rejects and cannot stop or cancel a newer action. Cancellation is an immediate
administrative removal, irrespective of the quantization argument; use Immediate
for clarity. A stopped/queued-only part stopped again needs no audio event.

Every due action is applied before writing its target sample. Multiple actions
can occur at different offsets inside one callback. Simultaneous eligible actions
use musical deadline, deck A before B, then slot order. Callbacks are half-open:
an event at their exclusive right edge belongs to the next callback. Replacement
and retrigger reset the selected source to one-shot frame zero or loop start.
Stop removes it before rendering the stop frame. Cancellation preserves the
current source cursor. One-shot EOF completes the reducer slot; a later pending
replacement remains queued, while a now-redundant stop is superseded.

Tickets expose Pending, Queued, Applied, Rejected, Cancelled and Superseded.
The ring also bounds observation history: after its row is reused, an old ticket
explicitly reports Expired, even if its musical action is still pending. The ID
can still identify that pending action for cancellation. This is not a durable
acknowledgement log. Queue-full admission returns an error without publication;
IDs are monotonic and refuse exhaustion before their 48-bit encoding wraps.
Dropping/failing the engine closes admission, and unresolved tickets report
Closed. Persistent UI event history is outside this milestone.

## Tempo changes preserve pending musical intent

Tempo requests install a future change at a musical boundary; Immediate tempo
edits reject. Beat/Bar are global; Phrase uses deck A's configured phrase epoch.
The timestamp argument is resolved at command ingestion using the current map.
The existing `TempoMap::edit_future` computes an unrounded fractional frame anchor
at that tick, preserves the preceding map, and replaces tempo intent from that
tick onward. A later edit at the same tick wins; an edit earlier than other future
changes supersedes those later changes. Past edits, invalid BPM and exhausted
storage reject without modifying the map.

Pending part deadlines stay in BeatTicks and are checked against the updated map
while rendering, so repeated edits retime them again instead of leaving stale
frame offsets. Tempo tickets mean Applied when map intent is installed, not when
the future tempo boundary has passed. Storage is reserved off-thread for at most
64 segments; no segment growth allocation occurs in rendering. Segment exhaustion
is an explicit error. Already rendered output is never retimed.

Sample material still plays at its prepared native rate and loop period. Tempo
edits change musical scheduling/phase; they do not time-stretch audio or silently
resample it. Fixed-rate loops may cease to align to beat phase after a tempo edit.

## Resident sources and existing audio buses

`LiveEngine::new` accepts up to 64 prepared SampleVoice templates, with unique
full Part definitions and at most 256 MiB canonical PCM across the resident bank.
Different configurations may share a PartId; full definitions disambiguate them.
Requests refer to bank indices; assets are never loaded or passed by ownership
through the queue. Each active slot has its own bank index and consumed-frame
cursor, so simultaneous launches of the same template do not share playback
position. Retrigger/replacement only change these fixed-size cursor records.
Old buffers remain owned by the bank until engine destruction.

Both eight-slot sums feed the existing mixer, crossfader, cue selection, independent
limiters, meters and validated output mapping. Cue remains pre-crossfader. This
path uses prepared sample boundaries and existing bus coefficient smoothing;
mid-source Stop/retrigger/replacement do not add a tail crossfade. Their state
and cursor changes are sample-accurate, but arbitrary nonzero discontinuities can
click. Prepared source fades do not imply a click-free arbitrary interruption.

`CpalPlayback::open_live` connects the prepared engine to the existing stream
lifecycle. Stream controls/destruction stay on the control thread; terminal stop
and new-stream recreation semantics remain those of M1. The live engine does not
finish merely because no part is playing. An unrecoverable scheduling error
latches failure and silences future work; callers observe the existing stream
monitor and recreate the engine off-thread.

The callback uses preallocated arrays/bank storage, stack values, atomic
loads/stores and single-attempt receipt CAS operations. There are no mutexes,
retry loops, filesystem/decoder calls, source destruction or allocations in its
normal render path. Per callback at most 32 commands enter and at most sixteen
part actions can be pending. Due dispatch is bounded to sixteen slot transitions
per frame; map lookup/edit work is bounded by 64 segments. No claim of hard
realtime deadlines is made without new load measurements.

## Reproduction and evidence

```
python scripts/validate_m1.py
cargo test -p audio-backend --test quantized --locked --offline
cargo run -p audio-backend --example sample_parts --locked --offline -- --fixture target/m2-fixture.wav
cargo run -p audio-backend --example quantized_parts --locked --offline -- target/m2-fixture.wav
cargo run -p audio-backend --example quantized_parts --locked --offline -- --check target/m2-fixture.wav
```

The offline trace at 48000 Hz starts deck A at beat 960/frame 24000. A tempo edit
to 60 BPM there moves deck B's epoch-relative phrase launch at tick 2880 to frame
120000. Four seconds render to global frame 192000. The new CPAL path built a
paused stereo f32/default-buffer stream on Speakers (HyperX Cloud III S Wireless).
No audible playback or new soak run was performed.

Tests cover before/on/after boundaries, Immediate rounding, half-open blocks,
sample output onsets/stops, multiple events within buffers, two decks and phase
epochs, replacement/retrigger, FIFO/cancellation/stale-ID precedence, EOF,
overflow/expiry/closed tickets, simultaneous producer/render activity, repeated
tempo edits, fractional anchors, high-tempo inverse rounding and edit capacity.
The offline audio/event matrix is identical across 1/31/128/511/8192/16384-frame
partitions at 44100/48000/96000 Hz. Existing M0–M2.2 tests remain in the workspace
gate. Final validation passed all 58 tests, formatting, workspace check, Clippy
with warnings denied, doc-tests and the dependency inventory. No new external
dependency or ASIO feature was introduced; the reviewed
Windows seven-package inventory remains unchanged. Hardware cue isolation,
dropout measurements and the previously noted release-license packaging gate
remain separate from these software results.
