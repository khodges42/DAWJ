# M1.4 master and headphone cue routing

`StereoMixer` now generates independent stereo master and cue buses, consuming
each source once per frame. `MixerControl::set_cue` atomically selects Off
(default), Deck A, Deck B, or Both. Cue taps after per-deck gain and before the
crossfader: a deck excluded from master by the crossfader remains available to
cue, but a deck with gain zero is silent on both. Both selected decks sum on cue.
The cue bus has its own 20 ms coefficient ramps, source-boundary fades, -18 dB
headroom, stereo-linked -18 dBFS sample-peak ceiling, and held stereo peak meters
(`cue_peaks`). Master and cue limiter state is separate: cue overload or selection
changes cannot duck or alter master. Cue is not a master/cue blend control.

The hardware-independent `render_buses` API exposes both buses for offline use.
`render_routed` interleaves them into one device stream. Neither API introduces
callback allocation, locks, filesystem I/O, blocking or source ownership changes.
The selection is a native x64 atomic word independent of the existing coherent
master parameter word; those two control updates are not transactional together.
Meter fields are independent lifetime peak observations, including the logical
cue bus even when no physical cue route exists. The limiter remains sample-peak
protection, not true-peak protection or a guarantee of safe listening volume.

## Explicit mapping and stereo fallback

`OutputRouting` uses zero-based stream channel indices, not connector names:

```rust
use audio_backend::routing::OutputRouting;
let four = OutputRouting::new(4, [0, 1], Some([2, 3]))?;
let custom = OutputRouting::new(6, [5, 2], Some([3, 0]))?;
let fallback = OutputRouting::stereo_master_only();
```

Master requires two distinct in-range channels. Cue, if requested, requires
another distinct pair with no overlap with master. Bad or overlapping maps fail
before hardware access. Unassigned channels and partial trailing frames are
silenced, including correct unsigned PCM silence. A non-stereo device may also
explicitly use master-only routing.

`CpalPlayback::open_routed_mixer` requires configuration and mapping channel counts
to match, then checks the exact rate/channel/encoding row and buffer request
against the selected device. The mapping stays fixed for the stream lifetime;
changing it requires reopening. Both buses share one device sample clock. There
is no multi-device aggregation or assumption that separate stereo endpoints
have synchronized clocks. Existing `open_mixer` deliberately stays stereo and
master-only; it never upgrades an endpoint or silently selects a different one.

`routing().cue_availability()` reports `DisabledMasterOnly` for fallback. Selecting
cue there can populate the logical cue meter, but sends no cue samples to the
device and never folds them into master. Requesting four channels on a stereo
endpoint fails explicitly; callers must choose the master-only fallback rather
than receiving a misleading promise of private monitoring. For a mapped cue pair
the status is `SeparateChannelsUnverified`: separate stream slots do not prove
headphone connector separation. No API labels an untested device as physically
verified private cue.

Ordinals are transient. This is an endpoint snapshot, not a professional-interface
or physical-connector inventory. The DualSense report must not be interpreted as
a verified main/headphone interface or permission to send cue to unknown outputs.

The new `routing_check` example never starts playback. With no arguments it lists
current capabilities; `--check <ordinal> <channels>` builds and drops a paused,
zero-amplitude stream at 48000 Hz f32 with the default buffer request. For >=4
channels it explicitly tries master [0,1], cue [2,3]; otherwise master-only.

```
cargo run -p audio-backend --example routing_check --locked --offline
cargo run -p audio-backend --example routing_check --locked --offline -- --check 3 2
cargo run -p audio-backend --example routing_check --locked --offline -- --check 5 4
```

Both paused builds passed: HyperX stereo with `DisabledMasterOnly`, and DualSense
four-channel with `SeparateChannelsUnverified`. Requesting four channels on
HyperX returned an explicit unsupported-configuration error (exit code 1).
No audio was played for M1.4. Paused construction does not verify callback timing,
physical signal isolation, headphone amplification, audible output or underruns.

## Will ASIO be needed?

Not for the implemented routing or the observed four-channel paused build. For
subsequent physical interface validation, the answer is still hardware-dependent:
if the intended main/headphone pairs are accessible together through the chosen
WASAPI endpoint, test those mappings first; if the required outputs are available
only through the vendor's ASIO driver, an ASIO backend will be needed. A channel
count alone does not establish either case. Vendor control-panel routing may
mirror outputs even when software stream channels are separate.
The HyperX's observed stereo endpoint cannot carry two separate stereo buses;
changing backend alone is not evidence that hardware has additional independent
outputs. A suitable physical interface still needs to be selected and checked.

The pinned [CPAL 0.15.3 WASAPI implementation](https://github.com/RustAudio/cpal/blob/v0.15.3/src/host/wasapi/device.rs)
uses shared mode and derives its enumerated channel count from the endpoint mix
format. It does not probe every hardware output arrangement. Microsoft describes
[`GetMixFormat`](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-getmixformat)
as the shared-mode engine's format, which need not equal the hardware's format.
Thus this inspection does not establish that all outputs of a multichannel
interface are available via WASAPI, nor that exclusive mode would expose them.

[CPAL's pinned README](https://github.com/RustAudio/cpal/blob/v0.15.3/README.md)
describes its optional ASIO backend. ASIO remains disabled here. Before enabling
it, review the exact added crates, SDK source/version and license obligations,
driver requirements and distribution plan against GPL-3.0-or-later policy. No
SDK download, new dependency, or ASIO hardware validation occurred in this task.
The existing seven-package Windows inventory is unchanged.
